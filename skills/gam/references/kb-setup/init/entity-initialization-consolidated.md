# GAM Entity Initialization — Consolidated Pattern
DEFAULT initialization pattern. Per-entity SDTs (derived from EOs) + ONE master DataProvider + ONE master Procedure for all required entities

---

## When to Use
- `consolidated` (DEFAULT) — any scenario: single entity, multiple entities, production, full-KB init, CI/CD deploy. Use this file
- `individual` — incremental setup, learning. See [GAM Entity Initialization — Declarative Pattern](entity-initialization.md)

---

## Object Structure
### Per-entity SDTs
For every GAM entity to initialize:

Apply the [SDT Generation Workflow](../../global-constraints.md#sdt-generation-workflow--derive-the-sdt-11-from-the-eo) to every entity (root and nested) before applying the rules below

a. Read the EO in `ref/GeneXusSecurity/` (locate by content header, not by an assumed file name —
   see [global-constraints.md § Where GAM's EOs live](../../global-constraints.md#where-gams-eos-live))
   and identify child entities:
	* Methods returning collections (`GetPermissions`, `GetRoles`, `GetMenus`, …)
	* `Add*` methods accepting sub-entity objects
	* Collection-typed properties

b. For each entity-internal child identified (e.g., Permissions inside Application, Options inside Menu):
	* Generate a dedicated `<ChildEntity>Definition` SDT
	* In the parent SDT, add a member typed as that child SDT with `Collection = 'True'`
	  (1:N by EO — verify in the EO file)

c. Recurse to the depth required by the user. A child entity with its own children follows the same rule

d. All `DataType` values come from the EO's `BasedOn` field — apply the
   [EO Discovery Protocol](../../global-constraints.md#eo-discovery-protocol-mandatory). Never infer or assume types

### Master SDT — `<Name>InitializationDefinition`
The single SDT the DataProvider returns. Wraps all entity collections in one place

- **Default name**: `GAMInitializationDefinition` — suggest this as default; accept any name the user prefers
- **All top-level entity members are `Collection = 'True'`** — unconditionally, regardless of how many instances are being initialized
- **Sole exception**: `Repository` is a scalar member. **Why**: GAM platform guarantees exactly one repository; `new()` is forbidden and a second instance can never be added
- Even when initializing exactly 1 Application: it lives inside `Applications { Item { … } }` — never as a scalar member

Typical member shape (include only entities being initialized):

```
<Name>InitializationDefinition
  Repository              GAMRepositoryDefinition         (scalar — exception)
  SecurityPolicies        GAMSecurityPolicyDefinition     (Collection = 'True')
  Applications            GAMApplicationDefinition        (Collection = 'True')
  Roles                   GAMRoleDefinition               (Collection = 'True')
  Users                   GAMUserDefinition               (Collection = 'True')
  AuthenticationTypes     GAMAuthenticationTypeDefinition (Collection = 'True')
  EventSubscriptions      GAMEventSubscriptionDefinition  (Collection = 'True')
```

Member naming: plural English noun, no suffix. Child SDT: singular `<Entity>Definition`

### Master DataProvider `Init<Name>GAMData`
- The only DataProvider in the consolidated pattern
- `Output` = the Master SDT (e.g., `GAMInitializationDefinition`)
- Defines all initialization values inline
- Each top-level entity collection uses `<MemberName> { Item { … } }` blocks — even when there is only one instance:
	```
	Applications {
		Item { Name = !"MyApp" ... }
	}
	Users {
		Item { Email = !"admin@example.com" ... }
	}
	```
- **`GUID` for all entities** (Repository, Role, User, Application): omit from the DataProvider by default — GAM auto-generates on `Save()`. Only populate when stable cross-environment GUIDs are required (see [MyGUIDs — Stable GUID Constants](entity-initialization.md#myguids--stable-guid-constants-optional))
- **`Login` for GAMUser**: omit — auto-generated by GAM on `Save()`
- `ClientId` and `ClientSecret` for applications: omit by default so GAM auto-generates. Populate only when the user supplies explicit values (DP-A2 `specific`)
- `#Properties`: `Output = "<MasterSDTName>"`, `IntegratedSecurityLevel = "SecurityNone"`

### Master Procedure `Init<Name>GAM`
- The only Procedure in the consolidated pattern
- Calls the master DataProvider: `&Master = Init<Name>GAMData()`
- Accesses `Repository` as `&Master.Repository` (scalar; no loop)
- Delegates each collection entity to a dedicated `Sub` routine; each `Sub` iterates its top-level collection with `For`:
	```
	For &GAMApplicationDefinition in &Master.Applications
		Do "InitApplication"
	EndFor
	```
- Even when the collection has exactly 1 Item, use the `For` loop — adding more instances later requires no Procedure change
- Orchestrates entity creation in dependency order (see "Initialization Order" below)
- `#Properties`: `IntegratedSecurityLevel = "SecurityNone"`, `MainProgram = true`, `CallProtocol = "Command Line"`

## Initialization Order
Order is mandatory — each step depends on the previous one being committed:

- `GAMRepository` — root of all GAM entities; no dependencies
- `GAMSecurityPolicy` — may depend on the repository; roles reference it via `SecurityPolicyId`
- `GAMApplication` — Permissions live inside the Application; must exist before Roles are assigned permissions
- `GAMRole` — references Application Permissions; both Application and SecurityPolicy must exist first
- `GAMUser` — role assignment requires Roles to exist
- `GAMEventSubscription` — depends on Application and Repository

For entities not listed: infer order from their code-provider files and their EO dependencies

---

## Idempotency per Entity
Idempotency strategies apply **inside the `For` loop** that iterates the entity's top-level collection (except `Repository`, which is accessed as a scalar member of the Master SDT)

- `GAMRepository`: Strategy C, scalar member `&Master.Repository`; `GetId()` → `Load`. No `For` loop
- `GAMSecurityPolicy` — see [GAMSecurityPolicy Code Provider](code-provider/gamsecuritypolicy-code-provider.md)
- `GAMApplication` — Strategy A: `GetByGUID` → `Load(Id)` when GUID provided; name lookup via
  `GetApplications(filter)` when GUID empty (DP-A1 `new` branch). GUID auto-generated — omit from DataProvider
- `GAMRole` — Strategy A: `GetByGUID` → `Load(Id)` when GUID provided; `GetRoles(filter.Name)` when
  GUID empty. GUID auto-generated — omit from DataProvider
- `GAMUser` — Strategy D: `Load(GUID)` void → check `GUID.IsEmpty()` → `new()` if empty
  GUID and Login auto-generated — omit both from DataProvider. When no GUID: use `GetUsers(filter.Email)`
  Do NOT check `Success()` after Load — see [GAMUser Code Provider](code-provider/gamuser-code-provider.md)
- `GAMEventSubscription`: Strategy B, filter lookup via `GAMRepository.GetEventSubscriptions` → `Load(Id)` or `new()`. See [GAMEventSubscription Code Provider](code-provider/gameventsubscription-code-provider.md); the handler program has its own contract in [GAM Events Subscription: Handler Contract](../../events/domain-event-subscription.md)

## Constraint — ClientSecret
In the master Procedure, after `GAMApplication.Save()` + `Commit`:

```genexus
If not &AppDef.ClientSecret.IsEmpty()
	If &GAMApplication.SetClientSecret(&AppDef.ClientSecret, &GAMErrors)
		Commit
	EndIf
EndIf
```

NEVER set `ClientSecret` as a property. See [GAMApplication Code Provider](code-provider/gamapplication-code-provider.md) — GAP 1
