# GAM Events Subscription: Handler Contract
GAM notifies a registered external program when a repository event occurs. This file covers the program that ATTENDS the event; registering the subscription by code lives in [GAMEventSubscription Code Provider](../kb-setup/init/code-provider/gameventsubscription-code-provider.md)

Event subscriptions work on any GAM release, and EO names below are the release ones. On the modular naming introduced in `GeneXusSecurity>=100`, currently in beta, the contract is identical with renamed EOs; translate them with the mapping in [global-constraints.md § GAM EO catalog](../global-constraints.md#gam-eo-catalog--names-and-roles-only-never-signatures)

## REQUIREMENTS
### Event catalog
The authoritative catalog is `ref/GeneXusSecurityCommon/#domains/GAMEvents.gx` (`Character(60)`); use exclusively the values defined there, without relying on external resource content

- Reference events by dot notation: `GeneXusSecurityCommon.GAMEvents.User_Insert`
- Never compare against a string literal; GAM passes the enum's stored value in `&EventName` and dot notation resolves it

### Handler signature
```genexus
parm(in: &EventName, in: &JsonIn, out: &JsonOut);
```

- `&EventName`: `GAMEvents, GeneXusSecurityCommon`
- `&JsonIn`: `LongVarChar(2M)`, payload serialized by GAM, format depends on the event
- `&JsonOut`: `LongVarChar(2M)`, interpreted by GAM per event (see "JsonOut semantics")

### Object properties
- `MainProgram = "True"`: mandatory; without it GAM has no entry point and the handler is never called
- `IntegratedSecurityLevel = "None"`: the handler runs inside GAM's own flow, before a session exists on some events
- `Execute in new LUW`: optional; set it when the handler must commit independently of the operation that fired it

### Execution semantics
- `Repository_Login` and `Repository_Logout` perform an implicit commit; handlers not generated by GeneXus always run in a separate LUW
- Events fire synchronously and blocking with no default timeout; a slow handler blocks the operation that fired it
- Only subscriptions whose `Status` is `Subscribed` run
- On login, events fire before the session is persisted, so a handler that writes into the session can invalidate the fresh token

### Payload per event
Deserialize `&JsonIn` into the EO below with `FromJsonString`; never parse the JSON by hand

- `User_Insert` / `User_Update` / `User_Delete`: `GAMUser`
- `User_UpdateRoles`: collection of `GAMGUID, GeneXusSecurityCommon`, the role GUIDs, not a `GAMUser`
- `User_GetCustomInfo`: `GAMSession`
- `User_SaveCustomInfo`: free format, the custom-info payload as the client sent it
- `Role_Insert` / `Role_Update` / `Role_Delete`: `GAMRole`
- `Repository_Login` / `Repository_LoginFailed` / `Repository_Logout` / `Repository_RememberAuthentication`: `GAMSession`
- `ExternalAuthentication_Response`: `GAMExternalAuthenticationResponse`
- `Application_CheckPermissionFail`: `GAMSessionLogCheckPermissionFail`
- the four OTP events: `GAMOTPEventSubscription`

`User_UpdateRoles` is the entry most often gotten wrong; a `GAMUser`-shaped deserialization silently yields an empty object

### JsonOut semantics
`&JsonOut` is the handler's only output and its meaning depends on the event

- `Repository_Login`: a non-empty value carrying an error object (code AND message both set) revokes the login and GAM reports that error; anything else is ignored and the login proceeds
- OTP events: any non-empty value aborts the OTP step; an error object is reported as-is, anything else as a generic OTP event error
- `User_GetCustomInfo`: the value IS data, returned as the custom info of the UserInfo response
- All other events: the value only reaches the GAM trace

GAM loads and returns the errors; a handler never builds, receives or iterates a `GAMErrorCollection`, and contributes to it only by returning an error object in `&JsonOut` on the events above

### Custom info round-trip
`User_GetCustomInfo` and `User_SaveCustomInfo` pair with two `GAMSession` methods, with the application-owned payload travelling as free-format JSON

- `GAMSession.GetApplicationData()`: returns the stored payload; assign it to `&JsonOut` on `User_GetCustomInfo`
- `GAMSession.SetApplicationData(json, out errors)`: stores it; returns Boolean, so it needs an assignment target

### OTP events need one extra wiring step
The four OTP events are resolved through an ID property on the OTP authentication type, not by event name. Creating the subscription and calling `SubscribeEvent` is not enough; the subscription's ID must also be set on the matching property of the OTP authentication type. Read that EO for the property names, see [OTP/TOTP auth type init by code](../authentication/local-sp/domain-otp.md)

### Registration: FileName / ClassName / MethodName
The subscription record points at a compiled entry point and GAM invokes it with the three registered values verbatim, so they must match whatever is deployed

For a handler generated by GeneXus the values follow the main-program wrapper convention:
- `MethodName`: `execute`
- .NET / .NET Framework: `FileName` = `a<objectname>.dll`, `ClassName` = `<CSHARP_NAME_SPACE>.a<objectname-lowercase>`
- Java: `FileName` = `a<objectname>.class`, `ClassName` = `<package>.a<objectname-lowercase>`

A handler implemented outside GeneXus registers its own file, class and method names; the `a` prefix and `execute` are the GeneXus wrapper convention, not a GAM constraint

Placing a GeneXus handler inside a `Module` changes the generated namespace and therefore the `ClassName` to register. A wrong `ClassName` fails silently: GAM never invokes the handler and emits no error and no trace, which is indistinguishable from an event that did not fire. `Folder` containers (`@name`) do not affect the generated name

## RECOMMENDATIONS
### Dispatch pattern
One `Do Case` on `&EventName`, one `Sub` per attended event, `Otherwise` for the rest

```genexus
Do Case
	Case &EventName = GeneXusSecurityCommon.GAMEvents.Repository_Login
		Do "OnRepositoryLogin"

	Otherwise
		Do "OnUnhandledEvent"
EndCase
```

Inside each `Sub`, deserialize into the EO declared with its `DataType` (`DataType = 'GAMSession, GeneXusSecurity'`): `&Session.FromJsonString(&JsonIn)`

### Keep JsonOut empty unless the intent is to stop the flow
On `Repository_Login` and the OTP events `&JsonOut` is a control channel, not a log; a diagnostic object that happens to carry code/message fields revokes a login or aborts an OTP step. Log diagnostics with `GeneXus.Common.Log.Write` instead

### Place a GeneXus handler in the Root Module
It keeps the generated namespace, and therefore the `ClassName` to register, independent of the module tree. Otherwise resolve the generated name empirically before registering it

### Verify the generated class after building
Confirm the class exists with the expected name in the generator's build output before trusting the registration; this is the only binding in the flow that fails without diagnostics

- .NET / .NET Core: the generated source declares `namespace <CSHARP_NAME_SPACE>` and `class a<objectname-lowercase>`, and the assembly must be present in the deploy output
- Java: `a<objectname>.class` under the package folder of the build tree

## DIAGNOSTICS
Trace signatures (format B) separate "the event did not fire" from "the binding is wrong"

- `genexus.security.api.ExecuteEventSubscriptions - Start_Method - {"data":{"EventName":"<stored value>"}}`: the event fired
- `genexus.security.api.ExecuteEventSubscriptions - Start_Sub-ExecuteExternalObject - {"data":{…}}`: GAM resolved a binding and is invoking it, and the payload carries the registered `FileName`

Then, in order, because each step rules out the next:

- No `Start_Method` for the event: the operation never reached the event
- `Start_Method` but no `Start_Sub-ExecuteExternalObject`: no active subscription, because `Status` is `Unsubscribed` and `GAMRepository.SubscribeEvent` was never called, or the subscription lives in another repository, or for OTP events its ID is not set on the OTP authentication type
- `Start_Sub-ExecuteExternalObject` with values that do not match the deployed class: fix the registration
- Values match but nothing happens: `MainProgram` is not `True`, or the assembly or class is missing from the deploy output

Traces must be active first, see [GAM Debugging Core](../debugging/common-debugging.md#activating-gam-traces-3-step-process)
